# 圖說 PDF 差異比對 → Revit 修訂雲

兩份 PDF 圖說（建築師給的舊版與新版）自動找出差異，依圖號對應到 Revit 圖紙，
把差異區域圈成修訂雲，並讓既有的釋疑管線接手。

## 適用與不適用

| 情況 | 支援 | 說明 |
|---|---|---|
| 兩份向量 PDF（Revit／CAD 匯出） | ✅ | 本方法的目標場景 |
| 掃描件、圖片轉存的 PDF | ❌ | 沒有文字層與向量指令，本方法完全無效。必須明確回報 `scanned`，**不可回報「無差異」** |
| PDF vs Revit 模型現況 | ❌ | 需先從 Revit 出 PDF；Revit 2020 無 `PDFExportOptions`（2022+ 才有），本 fork 不走這條 |
| 雲形跟隨模型幾何 | ❌ | 雲畫在圖紙（ViewSheet）上，見下方〈為什麼畫在圖紙上〉 |

## 核心設計判斷

### 為什麼是向量比對，不是影像比對或 AI 判讀

向量 PDF 的文字與線條座標就在檔案裡，直接比座標比「算成圖再比像素」精準一個
量級，也不受抗鋸齒與 DPI 影響，而且**零 API 成本、可離線、結果可解釋**
（能講出「這個位置的 CH=300 變成 CH=320」，而不是「這裡看起來不一樣」）。

AI 語意判讀（把差異區域截圖丟給 VLM，產出「天花高度由 CH=300 變更為 CH=320，
高信心」這種描述）是**另一層**，可以疊加在本方法之上，但不是本方法的替代品：
先要有可靠的「哪裡不一樣」，才談得上「不一樣在哪、重不重要」。

### 為什麼畫在圖紙上（ViewSheet），不是畫進視圖裡

PDF 頁座標 → 圖紙紙面座標是**單純的比例對應**，不需要 viewport／crop／scale
換算，位置最不會歪。畫進視圖裡雖然能讓雲跟著模型幾何跑，但要多經過一層
viewport 換算，PDF 若非本模型輸出就容易偏移。

取捨的代價：改模型後雲不會跟著移動。對「圖說變更追蹤」這個用途是可接受的——
雲標記的是「這一版圖跟上一版差在這裡」，本來就是對某一版圖紙的註記。

要改成畫進視圖時，`MCP/Core/Commands/CommandExecutor.ViewportPosition.cs`
已經有解好的「圖紙座標 ↔ 視圖模型座標」換算可以沿用。

## 假差異抑制：三道防線

**這種工具的失敗方式不是「找不到差異」，是「整頁都亮起來」。** 兩版 PDF 若由
不同 Revit 版本或不同 PDF 引擎輸出，同一條線可能被拆成不同數量的 segment、
同一段文字可能被切成不同的 span。三道防線依序上場：

### 第一道：座標量化（`quantum`，預設 0.5pt ≈ 0.18mm）

把座標對齊到量化格再比對，吸收次像素抖動。

**量化必然有邊界問題**：兩個只差 0.02pt 的座標若剛好跨在格線兩側（`60.24` 與
`60.26`），量化後會變成 `60.0` 與 `60.5`，被誤判成差異。所以每個圖元同時算
「原格網」與「偏移半格的格網」兩組指紋，比對時兩輪，任一輪對上就算相同。
跨界的座標在原格網分開、在半格格網一定合併，反之亦然——兩張格網不會同時失敗。

### 第二道：全域平移對齊

用「兩頁都存在且唯一的文字」當錨點，取平移量的**中位數**。

- 只取唯一的文字：重複出現的文字（"1"、"mm"、圖層名）配對會亂跳。
- 取中位數不取平均：少數真的被移動過的錨點不能把整頁推歪。
- 錨點少於 8 個就放棄對齊（回 `(0, 0)`）：寧可不對齊，也不要用三四個點亂推。

> ⚠️ **平移一定要在量化「之前」做。** 先量化再平移再量化一次會整格偏掉——
> 第一次量化已經把「該落在哪一格」所需的次量化資訊丟掉了。
>
> 實測案例（A1 圖說整頁平移 7.3pt）：B 的 `2131.2370` 先量化成 `2131.0`、
> 扣掉位移成 `2123.6999`、再量化變 `2123.5`；而 A 的 `2123.9370` 直接量化是
> `2124.0`。同一條線，差一整格。這個 bug 讓假差異從 10 個暴增到 82 個。

### 第三道：鄰近分群 + 最大空隙切開

**不要用「固定格網 + 相鄰格連通合併」。** 那是 all-or-nothing：格子只要連成
一串就滾雪球。實測一份真實圖說，第 2 頁的差異散佈全頁，連通合併後產出**一個
涵蓋 100% 頁面的區域**——準確，但圈成雲等於沒圈。

正解分三步：

1. **鄰近分群**：用 eps（預設頁面短邊的 3%，A3 約 9mm）大小的格子做桶，
   8-鄰域相連的桶算同一群。等價於 Chebyshev 距離的 DBSCAN，但是 O(n)。
2. **超過上限就切**：群的跨距超標時，沿較長的軸把點排序，找**最大的空隙**
   切開，遞迴處理兩半。
3. **切在空隙處，不是切在中位數**。中位數會把一團連續的東西硬切兩半，產生
   兩個都不自然的框；切在最大空隙等於「這裡本來就是分開的兩堆」。

> ⚠️ **切割判定要用軸向跨距，不能用面積。** 一排沿著同一條線的尺寸變更，外框
> 高度是 0、面積也是 0，用面積判定永遠不會切——結果是一朵橫跨整頁的扁長雲，
> 比不切還糟。改看「寬度佔頁寬多少、高度佔頁高多少」，任一超標就切
> （`maxSpanFraction`，預設 0.30）。

**找不到夠大的空隙就停手並標記 `oversized`。** 那代表這一區是**真的**整片都
變了。這時候誠實回報範圍，比硬切成幾個假的小框有用——後者會讓人以為只有那幾處
要看。

改用鄰近分群後的實測對比（同一份 A3 圖說 14 頁）：

| | 固定格網連通 | 鄰近分群＋空隙切開 |
|---|---|---|
| 第 1 頁最大區域 | 佔頁面 50% | 佔頁面 32% |
| 第 3 頁最大區域 | 佔頁面 25.9% | 佔頁面 **2.6%** |
| 全案可圈雲區域 | ~14 個 | **138 個** |

**門檻與權重是一組的**（預設 threshold=3、文字權重 3、線條權重 1）：
一處文字變更本身就構成一個區域，但要三條線對不上才算。這個不對稱是刻意的——
文字變更幾乎一定有意義，一兩條線配不上多半是量化殘差。

格號（`F5:F7`）用試算表式編號保留，因為那是使用者看得懂、講得出口的定位語言；
但**外框貼著差異點本身**，不再被格網撐大——那正是雲變小的原因。

### 兩組區域，回答兩個不同的問題

| 欄位 | 來源 | 回答什麼 |
|---|---|---|
| `regions` | 全部差異 | 「這頁改了多少」。真實圖說改版時它幾乎一定有一大塊 |
| `textRegions` | 只用文字差異 | 「哪幾個位置可以圈雲」。多半是佔頁面 1~2% 的小框 |

不能只留一組：全部差異算出來的大塊即使含有文字變更，框也大到沒有意義；而只看
文字會漏掉「這頁被重畫了」這個同樣要緊的事實。**UI 預設用 `textRegions`**。

### 標題欄的版次戳記要排除

實測 14 頁**每一頁**的標題欄都出現 `B版` → `C(working)`。那是「這份圖說改版
了」的證據，不是「這個位置的圖面改了」，圈成雲只會在每張圖右下角留一朵無意義
的雲。預設排除標題欄區域（`excludeTitleBlock`），可關閉。

### 舊圖既有修訂雲要先排除

舊版 PDF 可能已經帶著前一版的 Revit Revision Cloud。那些雲是歷史註記，不是本次
舊／新 PDF 的圖面差異；若直接把 Bézier 弧線拿去 fingerprint，會產生一批新增／刪除
線條，最後又在 Revit 重複圈一次。

`pdf_diff_worker` 在指紋化前對**舊版與新版兩邊**做向量排除：只接受 stroke-only 的
cubic 弧線，且必須同時符合「至少 8 段、至少 4 個獨立 path、端點近似封閉、外框最大邊
至少 8 pt」四個條件。這會排除實際 PDF 的修訂雲，也保留一般單一路徑圓弧與小型設備
符號。接著再用已辨識雲的外框（含 24 pt 緩衝，涵蓋雲旁的詳圖名稱）遮罩雲內的版次泡泡文字與其他差異，避免
只刪弧線卻又因 `8-9` → `6-7` 把同一朵歷史雲重新圈回來。每頁結果會回報
`revisionCloudsA/B` 與 `revisionCloudMaskedDiffs`，UI 也顯示剔除前／後圖元數並留下警告，
方便使用者在建立新雲前核對。

偵測值可用 `revisionCloudEndpointTolerancePt`、`minRevisionCloudCurves`、
`minRevisionCloudPaths`、`minRevisionCloudSizePt` 調整；預設值是依目前 14 頁實際
PDF 校準的起點，不代表所有事務所的 PDF 都不需重新校準。

### 參數必須可調，而且新案子一定要校準

預設值是起點，不是定論。**新案子的第一件事是拿實際的兩份 PDF 跑一次**，看
`itemCountA → itemCountB`（圖元總數）與區域數是否合理。

> 實測那份圖說：第 2 頁 14,803 → 22,007 個圖元（**+49%**）、第 7 頁 −31%、
> 第 12 頁 −28%。把量化格從 0.5pt 放寬到 2.0pt，差異只從 13,551 掉到 12,186
> ——**這證明那不是假差異，是圖真的大改**。圖元總數是「這頁到底改了多少」
> 最誠實的單一指標，一定要回報給使用者，否則他無從判斷該不該相信那幾朵雲。

## PDF → Revit 圖紙的座標換算

兩個必踩的陷阱：

1. **y 軸方向相反。** PyMuPDF 原點左上、y 向下；Revit `sheet.Outline`
   （`BoundingBoxUV`）原點左下、y 向上。少翻一次，雲會上下顛倒地出現在圖紙
   的另一半——而且因為它「有動」，肉眼很容易誤以為程式正常。
2. **用比例對應，不要做單位換算。** PDF 是 point、Revit 是 foot，但直接算
   `pt/864` 只在「PDF 頁完全等於圖紙外框」時才對。用兩個矩形的比例對應
   同時吸收了 PDF 邊界裁切造成的偏移。

```
u = Min.U + (x_pt / page_w) * (Max.U - Min.U)
v = Min.V + (1 - y_pt / page_h) * (Max.V - Min.V)     ← 這個 1- 就是翻轉
```

換算後要**重新取 min/max**：翻轉後 v 的大小順序會反過來。

**長寬比檢查**是唯一便宜又有效的「配錯圖紙」偵測：A1 的 PDF 配到 A3 的圖紙，
比例對應仍然算得出座標、雲仍然畫得出來，只是全部的位置都是錯的。長寬比一比
就露餡。這是警告不是阻擋——比例略有出入的圖框實務上存在，接不接受是使用者的判斷。

## 旋轉頁：PyMuPDF 會騙人

**建築 PDF 幾乎都是旋轉頁，而這件事會讓所有座標計算失效。**

`page.get_text()` 與 `page.get_drawings()` 回傳的座標在**未旋轉**空間
（`mediabox`，例如 842×1191），但 `page.rect` 是**旋轉後**的顯示尺寸
（1191×842）。拿後者去正規化前者，比例會超過 100%，圖框位置整個找錯。

> 實測一份 A3 橫式圖說（`page.rotation == 90`）：標題欄文字的 y 座標算出來是
> 頁高的 **118.4%**。右下角搜尋區完全掃不到任何文字，圖號抽取全滅。

修法：把文字與幾何**都**套 `page.rotation_matrix` 轉到顯示空間。一律轉到
顯示座標而非反過來——使用者看到的、以及 Revit 圖紙上的方位都是旋轉後的樣子，
雲必須落在使用者看到差異的地方。**文字與幾何必須在同一個座標空間**，否則
全域對齊會拿文字算出一個平移量、套到幾何上卻是錯的方向。

## 圖號與圖名抽取：標籤優先，regex 備援

### 為什麼 regex 是備援不是主力

圖號格式每家事務所都不一樣。實測一份真實圖說的圖號是 `0721B-ARD-D02001`，
任何合理的通用 regex 都接不到；台灣圖說也常用中文前綴（建／結／電／給排水），
預設的 `^[A-Z]...` 一個都接不到。

但**圖框裡幾乎一定印著欄位標籤**：`DWG NO.`、`圖號`、`SHEET NO.`。用標籤定位
不需要猜圖框在頁面哪個角落（標籤自己會說），也不需要使用者先看懂自己的圖號
格式再去寫 pattern。

> 實測結果：標籤定位在該份圖說的 **14 頁全中**，新舊兩版一一對應。

### 標籤定位的兩個坑

1. **方向要用 bbox 邊緣判定，不能用中心點。** 實測 `ISSUE NO.` 的中心只比
   `DWG NO.` 右 0.7pt——它其實在**正下方**，卻因為 `cx > lx` 成立就被算成
   「右方」，而右方的距離公式又讓它贏過真正的值。改成「右方的值必須整個落在
   標籤右緣之外」語意就對了。
2. **欄位標籤永遠不是欄位值。** `DWG NO.` 正下方 24pt 處就是 `ISSUE NO.`，
   不排掉就會把它當圖號抓走。排除規則見 `looks_like_field_label()`。

### 圖名：跨頁比對才選得準

沒有 `DWG TITLE` 標籤時退回字級啟發式（標題欄裡圖名通常是最大的字之一）。
但單看一頁會挑錯：實測那份圖說字級最大的是專案名
`統一企業集團桃園U-PARK智匯產業園區`（12.4pt），真正的圖名
`地下一層平面圖` 只有 11pt。

**專案名每一頁都一模一樣，那正是它當不了圖名的原因**——圖名的職責是區分這一頁
與其他頁。所以規則是：**在所有頁面都出現的候選，一律不是圖名。** 這條規則不
依賴任何一家事務所的排版習慣。另外要排掉註記（`註:`／`NOTE`）——實測新版某頁
在標題欄附近多了一段註記，字級剛好比圖名大就把圖名擠掉了。

### 配對三輪

先嚴格（圖號原樣），再寬鬆（拿掉 `-`/`_`/空白），最後用圖名。順序不能顛倒——
`A-101` 與 `A101` 在很多案子裡是兩張不同的圖，寬鬆與圖名比對只當最後手段，
結果要標記讓使用者確認。

**三類全部攤開回傳**（配對成功／只在舊版／只在新版），一頁都不能吞掉：
「新版多了一張圖」跟「這張圖有變更」同樣是使用者要知道的事。回傳「候選清單」
而不是單一答案，UI 必須讓使用者從候選裡挑或直接手打。

## 與既有釋疑管線的銜接

差異說明寫進雲形的 `Comments`，這正是既有 `scan_revision_clouds` 讀出來放進
釋疑 Excel 的欄位。所以整條管線自動接得上：

```
PdfDiffClouds（本流程）→ 雲形 + Comments
  → 掃描釋疑 scan_revision_clouds  → 寫入釋疑編號（Mark）
  → 上圖紙 add_cloud_views_to_sheets（本流程的雲已在圖紙上，通常不需要）
  → 匯出釋疑 export_revision_excel → 釋疑清單 Excel 給外單位填回覆
```

Comments 的內容要能**獨立閱讀**，不能依賴 UI 上下文——它最後會出現在給外單位
的 Excel 裡。格式：`[F5:F7] CH=300 → CH=320`。

## UI 的驗證：離線 WPF 模擬器

這顆按鈕連續三次「全套測試綠、IronPython 編譯過、真實 PDF 端對端成功，
然後在 Revit 裡第一次點就炸」。三次的成因都不是演算法，是 **WPF 的物件模型**：

| 症狀 | 成因 |
|---|---|
| Revit 行程終止 | 快取的 ComboBox 被掛到第二個父層（切換下拉時重建左欄） |
| Revit 行程終止 | 同一張卡片在一次繪製裡加兩次（`(gridLabel, score)` 當快取 key 會撞） |
| **不崩潰、一朵雲都沒建** | `selected_pairings` 自己重組了一份 key，改了 `_box_for` 卻漏改它 |

純函式測試蓋不到這些（問題在 UI 的物件關係），CPython 也沒有 WPF 可以測。
解法是 `pyRevit_Tools/tests/test_pdf_diff_window.py`：**用假的 WPF 元件把
「單一父層」做成會拋例外的強制規約**（`Children.Add` 遇到已有父層的元素就丟，
`Children.Clear()` 只釋放直接子層——這正是「快取整張卡片安全、快取深層元件
會炸」的原因），再從 XAML 讀出所有 `x:Name` 建出對應的假控制項，然後真的驅動
視窗跑一遍：比對 → 選圖紙 → 換模式 → 勾選 → 取出結果。

三個 bug 都做過負向測試（放回去確認會失敗）。同一套 stub 也順帶驗證了
**程式碼引用的每個控制項名稱都真的存在於 XAML**——名字打錯在 Revit 裡是
AttributeError，在這裡會在 CI 就爆。

> 兩件事這支測不到，要靠別的關卡：IronPython 與 CPython 的行為差異
> （`'{:.2f}'.format(0)` 只在 IronPython 丟 ValueError，見
> `format_fraction_percent` 的型別不變量），以及版面外觀。

## 大型專案的成本模型（2026-09-02）

使用者回報：「圖說差異修訂雲」與「放置修訂雲標籤」在大型專案「點下去會跑
很久，然後直接當機發生嚴重錯誤」。成因不是任何一個函式寫錯，而是四個
**只有在大案子才看得出來的複雜度問題**，全部發生在 Revit 的 UI 執行緒上。
下面是必須維持的成本上限；改動這兩顆按鈕時請一併確認沒有退回去。

| 規則 | 反例（會炸的舊寫法） | 為什麼 |
|---|---|---|
| 圖框用一個全文件 collector，再依 `OwnerViewId` 分組 | 每張圖紙一個 `FilteredElementCollector(doc, sheet.Id)` | 1000 張圖紙就是 1000 個 view-scoped collector |
| `element.Parameters` 每「種」元素只走訪一次，之後用 `LookupParameter` | 每張圖紙都走訪圖紙＋圖框 instance＋圖框 type 三張完整參數表 | 讀 `Definition.Name` 要跨 API 邊界；200 張圖紙＝600 次全表走訪 |
| 只掃 `OST_RevisionCloudTags` | `OfClass(IndependentTag)` 掃全文件標籤 | 大案子有幾萬個門窗／房間／牆標籤，修訂雲標籤只有幾十個 |
| `ElementId` 存取器解析一次就快取 | 每次都「先試 `Value` 再退回 `IntegerValue`」 | `Value` 是 Revit 2024 才有的；2020–2023 上每次呼叫都丟一次 AttributeError，而這支函式會被呼叫幾十萬次 |
| 圖紙勾選用 `id(row)` 集合查詢 | `row in selected_rows`（list 的線性搜尋） | `row` 是 dict，沒命中就走完整的深層比較，而 `row['page']` 底下掛著整頁的 region 清單；對每一列各做一次就是 O(N²) |
| 每頁的「對到哪張圖紙」下拉共用一份 `ItemsSource` | 每個下拉逐項 `Items.Add` | 1500 張圖紙 × 200 頁 ＝ 30 萬次跨 WPF 邊界呼叫，而且全發生在 `compare_clicked` 這個事件處理常式裡 |

實測（假 Revit，200 張圖紙）：collector 建構 201 → 2 次，參數表走訪
600 → 3 次，且 20 張與 500 張的次數完全相同。

兩個配套的結構決策：

* **「放置修訂雲標籤」先找雲、再找圖紙。** 只有真的有雲的圖紙需要昂貴的
  DWG NO. 欄位掃描，而那通常是幾十張、不是全部幾千張。清單也因此只列有雲的
  圖紙——沒有雲的圖紙在那個 UI 上什麼都不能做，列出來只是讓使用者多捲幾千列。
* **每個 WPF 事件處理常式都包 `_guard`。** WPF 不會替我們攔 dispatcher 上的
  未處理例外，Revit 只會顯示「發生嚴重錯誤，應用程式將終止」然後關掉，訊息
  還看不到。包起來至少會變成一個看得懂、可回報的對話框。這是最後一道網子，
  不是不用修成因的藉口。

守門的測試：`tests/test_pdf_diff_sources.py`（假 Revit 記錄 collector 建構與
參數表走訪次數，斷言不隨圖紙數成長）與 `tests/test_place_revision_cloud_tags.py`
（斷言 `sheet_records` 只被要求算有雲的圖紙、collector 用類別過濾）。
兩支都做過負向測試——把舊寫法放回去確認會失敗。**這類問題純功能斷言擋不住：
放寬掃描範圍不會改變任何一筆輸出，只會讓它變慢。**

## 環境需求

系統 Python 3 + `pip install pymupdf`。直譯器探測順序：`REVITMCP_PDF_PYTHON`
環境變數 → `py -3` → `python` → `python3` → 常見安裝路徑。

探測時會實際跑 `python -c "import fitz"` 確認**那一支**有 pymupdf——只確認
「Python 跑得起來」不夠，真正的失敗模式是「Python 有，但那一支沒裝套件」
（issue #93 的教訓）。錯誤訊息必須附上實際的直譯器路徑，否則使用者無從判斷。

## 已知限制

1. **量化殘差無法歸零。** 實測以 `show_pdf_page` 重新嵌入的 PDF（比真實情境更
   嚴苛），兩張格網都救不回來的殘差約 1/44 個圖元。門檻 3.0 可以濾掉，門檻 2.0
   不行。真實的兩份 Revit 匯出 PDF 殘差應該更低，但仍需逐案校準。
2. **改版幅度大的圖說，逐區圈雲本來就不適用。** 實測那份圖說每一頁都有一個
   `oversized` 區域，因為圖真的整張都動了。這種情況工具會誠實標示，該做的是
   整張圖重新檢視，而不是硬圈幾朵雲假裝只有那幾處要看。
3. **執行時間**：兩份 14 頁 A3（各約 1.7MB、單頁最多 22,007 個圖元）約 7.4 秒。
   worker 支援 `pages` 參數限定頁範圍，百頁級可分批。
4. **雲形不跟隨模型幾何。** 見上方〈為什麼畫在圖紙上〉。
5. **沒有 AI 語意判讀。** 只回報「這個區域有差異」與樣本前後值，不解釋
   「這個變更影響什麼」。資料結構已預留描述欄位。
6. **UI 元素沒有虛擬化。** 左欄圖紙卡片與右欄區域卡片都掛在 `StackPanel`
   裡，數量等於 PDF 頁數與該頁的區域數。上面的成本模型解掉的是「不該隨
   **專案規模**成長」的部分；如果單次比對就丟進幾百頁 PDF，卡片數本身仍會
   讓視窗變重。那時該用 worker 的 `pages` 參數分批，而不是硬開一次。
