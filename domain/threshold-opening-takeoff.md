# 門檻開口統計

本 Domain 工作流定義依房間關聯進行門/窗統計的方法，用於門檻與未來開口相關計算。

## 目的

套用專案指定的房間與類型排除規則後，統計屬於有效房間的開口。目前目標是不鏽鋼門檻數量；後續工作流可再將納入統計的門數乘以寬度，或依類型定義門檻長度。

## 支援的開口

- 門：門檻數量統計的主要工作流。
- 窗：可使用相同的房間兩側過濾模式，但在定義實際應用前，不預設特定公式。

## 必要資料

門：

- 使用 `get_room_door_counts`，並設定 `includeDoorDetails: true`。
- 對 `Doors` 使用 `query_elements_with_filter`，取得 `類型備註`、`類型`、`族群與類型`。

窗：

- 使用 `get_room_window_counts`，並設定 `includeWindowDetails: true`。
- 對 `Windows` 使用 `query_elements_with_filter`，取得模型中可用的類型備註/類型欄位。

## 門檻統計演算法

1. 查詢目標範圍的房間-門明細。
2. 將所有房間的 `Doors` 陣列攤平成單一清單。
3. 依 `ElementId` 去重。
4. 對每樘門，同時以 `FromRoomName` 與 `ToRoomName` 檢查房間排除規則。
5. 任一側符合時，整樘門排除。
6. 依 `ElementId` 合併類型參數資料。
7. 對 `類型` 與 `族群與類型` 檢查類型排除規則。
8. 類型文字符合時，整樘門排除。
9. 將剩餘門依 `類型備註` 分組。
10. 呈現各組數量與總數。

## 規則模型

房間排除可包含：

- 使用者提供的精確房名或包含比對房名。
- `機房`、`廁所`、`管道間` 等關鍵字規則。
- 後續專案指定的其他房間詞彙。

類型排除可包含：

- 類型名稱包含 `管道間`。
- 族群/類型文字包含 `鐵捲門`。
- 後續專案指定的其他類型或族群詞彙。

分組規則可包含：

- 預設以 `類型備註` 作為門編號。
- 只有在使用者明確要求時，才改用 `TypeMark`、`Mark` 或其他參數。

## 重要差異

- 房間排除與類型排除彼此獨立。任一條件命中即可排除該門。
- 門只要碰到被排除房間，即使另一側房間有效，也必須排除。
- 若門只有一側房間資料，在已知側有效且沒有類型規則排除時，仍可計入。
- `類型備註` 在此工作流中是類型參數，不是實體參數 `備註`。

## 輸出格式

目前門檻工作流優先使用：

```markdown
| 類型備註 | 數量 |
|---|---:|
| D3 | 2 |
```

當規則有變更時，需用一小段文字說明目前生效規則。

除非使用者要求，避免列出實體標註；此工作流中使用者將 `類型備註` 視為門編號。

## 未來門檻長度延伸

數量穩定後，門檻長度可透過以下資料串接計算：

- 納入統計的門 `ElementId`。
- 門類型寬度或類型名稱。
- `類型備註` 到門檻長度的人工對照表。
- 各類型數量。

在使用者定義長度來源前，不要計算長度。長度來源可能是實際門寬、名目類型名稱，或自訂明細表/對照表。

## 機房門檻長度工作流（已實作）

使用者已為「不銹鋼門檻（機房）」選定長度來源＝Revit 實際門寬，實作於 pyRevit 按鈕
`MachineRoomThresholdExcel`（`lib/machine_room_threshold_excel.py` 與純規則模組
`lib/machine_room_threshold_logic.py`）。此工作流與上方的「數量」統計是兩件事，
不要互相取代。

### 房間分類

1. 房名先做正規化：NFKC、轉小寫、`鏽`→`銹`、移除分隔符號。
2. 命中泵浦/電氣/送排風等關鍵字者為 `include`；只出現一般「機房」者為 `review`；其餘 `exclude`。
3. 英數關鍵字（`ups`、`mdf`、`ahu`、`mau`、`server`）必須落在拉丁字詞邊界上，
   避免 `GROUPS`、`MAUSOLEUM` 之類的名稱誤判；中日文關鍵字維持子字串比對。
4. 分類只決定**預設勾選**。最終納入哪些房間一律由使用者在 UI 勾選決定。

### 來源模型與樓層範圍

1. 房間來源＝**主模型＋使用者勾選的連結模型**。主模型永遠納入：本工項是全案總量，
   連結模型是加上去的，不是取代主模型。
2. 樓層篩選是**逐模型**生效：某個模型一個樓層都沒勾＝該模型全部樓層。
   只勾連結模型的 B1F，不會連帶把主模型變成「未選取樓層」而整個消失——
   使用者在勾選清單上看不見的房間，就無從發現它少了（見 Lessons L-015）。
3. 房間身分是 `(來源模型, ElementId)` 複合鍵，樓層身分是 `(來源模型, LevelId)`。
   ElementId 在主模型與各連結模型之間會重號，不可只用 ElementId 當索引鍵。
4. 房號同樣會跨模型撞號且指向完全不同房間（本案 `F125` 在主模型是電氣室、
   在鮮食中心連結是女廁）。房間與 `內牆` 索引的比對一律維持**房號＋房名雙鍵**，
   不可因為加了連結模型就簡化成只比房號。
5. 門與房間**必須在同一份文件內**比對：連結模型的門不會通到主模型的房間，反之亦然。
6. 連結模型在載入房間清單之後被卸載時，該來源的門寬無法取得，列為 blocker；
   靜靜貢獻 0 m 會讓總長無聲短少。
7. 預覽與視窗都必須明列「讀取範圍」（各模型各自的樓層與房間數），
   數字要能自己說出它是從哪些模型、哪些樓層來的。

### 門與長度

1. 逐門以「門本身的 `PHASE_CREATED` 階段」優先解析 `FromRoom` / `ToRoom`，
   其他階段只作備援；多階段模型不可用文件階段順序的第一個命中值。
2. 任一側房間屬於使用者勾選的機房，該門即納入。與「數量」工作流的排除邏輯方向相反，
   不要混用。
3. 長度＝納入門的 Revit 門寬（`DOOR_WIDTH`，退而求其次 `寬`/`Width`）總和，單位公尺。
4. 納入的門缺有效寬度是真實資料缺口，列為 blocker 並禁止寫入；
   未納入的門一律不列 blocker——與本工項無關的門不得阻擋更新。

### Excel 寫入契約

1. 以 `UsedRange.Value2`（每張工作表一次 COM 呼叫）讀取後在程式端比對工項標籤。
   **不可用 Excel 原生 `Range.Find`**：預算表的工項標籤常是跨表公式鏡像
   （例：`其他長度!C19` 內容為 `=小計!C93`），Find 在 `xlValues` 與 `xlFormulas`
   下都看不到這種儲存格，實測會漏掉唯一可寫入的目標。詳見 Lessons L-009。
   讀取上限被觸發且該表含工項時，視為無法確認唯一工項，列為 blocker。
2. 可寫入的工項必須在同一工作表上方找得到 `數量`/`長度` 表頭配對；
   彙總表（小計）與對照表（更新工項）的同名工項會因此被排除，
   剩下計算表上的那一列才是輸入格。
3. 長度值優先引用工作簿自己的開口索引，而不是寫死數字。
   索引分頁與寬度欄由程式**探索**（房間表頭 `編號`/`空間名稱` ＋唯一的 `寬` 欄），
   不得寫死分頁名；同時符合的分頁可能不只一張（本案 `內牆!M` 與 `踢腳!F` 都符合），
   由使用者在 UI 選擇，預設值取「相鄰工項列既有公式已經引用的那一張」。
   公式形如 `=SUM(內牆!M16:M20)+內牆!M30`：連續列壓成區段，
   **每段各自一個 SUM 再用 `+` 串接**，不可寫成單一個 SUM 塞進所有區段
   （.xls 的 30 引數上限，實務上一定會超過）。
   哪些列被加總由使用者勾選的房間決定（房號對應到索引列），
   Revit 門寬總和退為交叉驗算：不一致時在預覽明列差異，不阻擋寫入。
4. 沒有可用索引時，才退回可稽核的常數式：
   預設 `=0.9+1.8+…` 加法鏈（每樘門一項），超過該檔案格式的字元預算時
   退回 `=120*0.9+80*1.8` 分組式。**不可使用 `=SUM(...)`**：
   .xls 的函式引數上限是 30，門數超過即失敗（詳見 Lessons L-013）。
   原公式含儲存格引用或非白名單邏輯時禁止覆寫。
5. 寫入前備份、寫入後回讀驗證；驗證失敗或寫入過程發生例外時自動由備份還原，備份檔保留。
6. 重新定位、寫入、回讀必須在**同一個 Excel session** 內完成。
   在 Revit 這種長生命期宿主中反覆建立/結束 Excel 實例會產生無訊息的
   `COMException 0x800A03EC`（詳見 Lessons L-012）。各階段要有階段標記以便定位。
