# Revit 既有 Excel 活頁簿更新

## 目的

當 pyRevit/RevitMCP 按鈕必須更新既有估價活頁簿，而不是產生一份新的報表時，使用這份 domain。核心風險不只是算錯數量，而是把依賴隱含慣例、公式與跨分頁索引的小計活頁簿弄壞。

停車位 Excel 按鈕就是參考樣式：Revit 明細表提供車位數量，`其他數量` 放可編輯列，公式欄計算數量，`小計` 再把結果索引回去。

## 開發前先讀懂活頁簿

把活頁簿當作資料結構來看，不要只把它當成畫面上的表格：

- 活頁簿格式：`.xls` 或 `.xlsx`
- 目標工作表名稱
- 項目標籤欄
- 輸入欄
- 倍數欄
- 公式欄
- 小計或索引分頁
- 隱藏列或人工維護欄位
- 帶尺寸的列標籤，例如 `250*550` 或 `300*700`

在確認列身分穩定之前，不要硬編 `row number`。優先用正規化後的項目文字加上尺寸或單位提示來比對。若同一列可能匹配到多次，就先停下來，要求活頁簿慣例或補更嚴格的 matcher。

## 用明確邊界讀取 Revit 來源

在計數前先決定來源邊界：

- 如果明細表本身就是使用者意圖，就用精確明細表名稱。
- 只有在類別本身就是目標範圍時，才用 category collector。
- 只有 UI 明示「以目前選取為來源」時，才用 selected elements。

不要把特定專案觀察到的明細表名稱寫成永久前提。以停車位 Excel 為例，`汽車停車數量`、`大客車停車數量`、`機車停車數量` 可以是預設候選，但 UI 應允許：

- 自動偵測指定樓層所有 `OST_Parking` 元素。
- 由使用者複選實際要納入的停車明細表。
- 對複選來源用 `ElementId` 去重，避免同一車位被多張表重複計算。
- 專案地下室共通或車位放在建築連結模型時，提供「包含 Revit 連結中的 Parking 元素」選項；連結模型元素不可直接用 host LevelId 比對，需改用樓層名稱或高程輔助比對。
- 同一樓層若有多個連結模型，必須讓使用者明確複選連結實例，不可用「包含全部連結」代替。主模型明細表與指定連結應視為兩種獨立來源：主模型遵守明細表篩選；指定連結則在使用者確認的連結範圍內，依樓層、類別與尺寸分類。除非已證明兩邊參數語意一致，不可把主模型的 `標註／Comments` 篩選直接套到連結模型，因為連結中的同名欄位可能存放車位編號。

若是明細表來源，只收集該命名明細表中的元素，並以 `ElementId` 去重。除非使用者同意，否則不要把明細表偷換成原始類別收集；原始類別常混入符號、箭頭、輔助圖形或佔位元素。

如果來源元素包含 Revit 群組，效能風險會被放大：同一組內可能有大量重複族群實例，若每個元素都展開群組或掃描全部參數，UI 會明顯變慢。群組情境的預設策略是：

- 仍以使用者指定的明細表作為數量邊界，不展開 `Group` 成員另算一次。
- 對 `ElementId` 去重後才分類。
- 先用明細表種類、樓層與尺寸分類。
- 只有分類失敗的元素，才讀取較昂貴的文字參數或無障礙參數。
- 在預覽中顯示群組內元素數量，讓使用者知道慢速來源與計算邊界。

在寫回 Excel 前，保留來源紀錄：

```text
ElementId, SourceSchedule, Category, Level, TypeName,
Width, Depth, Units, Classification, Warnings
```

保留完整樓層名稱。在專案證據證明它們是別名之前，不要把 `B-B1F`、`B-1F` 和 `B1F` 合併成同一個 key。

## 用證據做分類

分類必須可重現：

- 大分類如汽車、大客車、機車，優先用精確明細表歸屬。
- 子分類用明確單位與容差的尺寸。
- 只有在尺寸不可用，或本來就刻意把尺寸當次要條件時，才用型別名稱或參數證據。
- 無法判定的項目放進 warnings，不要默默塞到最接近的類型。

以停車位標線為例，活頁簿尺寸通常是公分，Revit 幾何常是毫米。只轉換一次，並保留明確容差，例如 50 mm。

## 讓使用者擁有選項

當數量規則取決於採購或事務所慣例時，要把它做成 UI 選項，不要埋進程式碼。例如：

- 每個汽車停車位是 1 個還是 2 個塑膠車輪檔
- 目標樓層
- 目標活頁簿路徑
- 是否納入特殊明細表或選取元素

預覽必須顯示每個選項會如何改變即將寫入的儲存格。

## 只寫入活頁簿輸入格

把活頁簿視為合約：

- 只寫入像是數量欄、倍數欄這類輸入儲存格
- 保留公式、格式、列順序、分頁名稱與跨分頁參照
- 在寫入相鄰儲存格前先驗證公式
- 寫入前建立帶時間戳的備份
- 如果活頁簿目前已是唯讀狀態，就拒絕寫入

對脆弱的既有 `.xls` 檔，Excel COM 是可接受的，因為公式與舊格式往往必須交給 Excel 自己重算。COM 呼叫要盡量小：批次讀取 range、能避免逐格掃描就避免、可靠地關閉活頁簿，而且即使失敗也要釋放 Excel。

## 公式白名單

對每一個目標列，把公式正規化：移除空白、`$` 與工作表引號。只接受符合預期合約的公式形狀。若是簡單的「數量乘倍數」，可接受的公式如下：

```text
=Frow*Grow
=Grow*Frow
=PRODUCT(Frow,Grow)
=PRODUCT(Grow,Frow)
```

若公式含有額外參照、條件式、跨多列加總，或連到無關工作表，就要拒絕，除非那種活頁簿樣式已被明確審查過。

注意：公式白名單失敗應阻擋「寫入」，但不應阻擋「預覽」。預覽仍要列出 Revit 數量、目標列、舊值與實際公式，讓使用者知道要修哪一列。

## 公式位址治理

Excel 顯示 `#REF!` 只代表語法壞掉，不能證明公式仍指向正確資料。`=SUM(B2:B13)` 在新增第 14 列後仍是合法公式，但已少算一列，這種靜默錯誤必須用語意契約攔截。

- 列號與欄號只能是最後解析出的座標，不是資料身分。以唯一列標籤、欄名、材料代碼、型號鍵或定義名稱定位，再產生 A1 位址。
- 產生公式前先完成列排序、分區與合計列配置；不得先寫公式再假設後續插列會自動修正。
- 合計公式必須驗證「本欄、第一筆資料列、最後一筆資料列」三項都符合實際輸出區域。公式可計算但少一列，同樣要拒絕存檔。
- 跨分頁公式必須掃描整本活頁簿，不只 `小計`。所有直接引用受管理分頁總計列的公式，都要以該分頁的唯一總計標籤重新定位。
- 表頭列用必要欄名定位。固定第 3、4、5 列只能作舊檔相容備援，而且使用前必須驗證該列仍含預期欄名。
- 總計標籤、表頭錨點或資料列 key 不是唯一時停止，不得採第一個命中。
- 預覽與寫入分開時，寫入前要重新讀取目標 key、公式與保護狀態，防止確認期間插列或改公式造成 TOCTOU。
- 只有錯誤 token 掃描、成功重算或結果為數字，都不足以通過。還要比對公式形狀、參照邊界與獨立計算的總量。

涉及動態資料列的測試至少包含：在資料末端新增一列、在標題區插一列、材料欄重排、移除一個材料欄、其他分頁引用總計列，以及「公式合法但仍指向舊列」。

## 寫入後驗證

儲存並重新計算後，要驗證：

- 已變更的輸入儲存格等於預期值
- 受保護公式沒有被改掉
- 公式結果確實反映預期乘法
- 小計或索引分頁仍然正確參照目標分頁
- 所有分頁對受管理總計列的參照都已跟著唯一標籤移動
- 每個合計 `SUM` 的起訖列正好等於實際資料區域
- 活頁簿沒有新增 `#REF!`、`#VALUE!`、`#NAME?` 或 `#DIV/0!`

未解決的 warnings 要和成功寫入分開回報。只要 warnings 仍可能實質改變數量，就不能宣稱任務完成。

## OfficeCLI 輔助驗證（只針對 `.xlsx`）

OfficeCLI 可以補上「檔案已產生，但內容或版面悄悄錯掉」的離線檢查；它不是 Revit 數量計算器，也不是舊式 `.xls` 的替代 Excel 引擎。專案共用驗證腳本為：

```powershell
.\pyRevit_Tools\tools\verify-officecli-xlsx.ps1 `
  .\tmp\InteriorWallPaint_bottom_ray_test.xlsx
```

這支腳本會依序檢查：

- OpenXML package schema 是否有效
- 分頁、列欄數、公式數與錯誤儲存格統計
- `#REF!`、遺失分頁參照、公式無法評估、壞掉的定義名稱
- OfficeCLI 偵測到的合併儲存格文字溢位等版面警告
- 可選的 HTML 視覺檢查：`-RenderHtml -RenderPath <path>`

新建報表的 `.xlsx` 應把公式問題視為失敗；版面警告預設只列為 warning，因為既有列高可能是使用者刻意調整的，必要時可加 `-FailOnLayoutWarnings`。HTML 或 `query` 讀回的字體、大小、合併與四邊框線，應拿使用者確認過的樣式副本作為比較基準，不能由工具自行重排活頁簿。

既有工作簿若是 `.xls`，仍由 Excel COM 負責讀寫、重算、保留桌面樣式與備份；既有 `.xlsx` 的 COM 發佈完成且 Excel 關閉後，可再用這支腳本做結構/版面 read-back。不要在 IronPython 按鈕內無條件啟動 OfficeCLI，避免 Revit 內的外部程序、PATH 或 OfficeCLI 版本差異讓原本可用的匯出流程失敗。

## 測試樣式

把純邏輯放到 `lib/`，讓 pyRevit 按鈕維持輕薄。至少要做以下單元測試：

- 列標籤正規化
- 唯一列比對
- 公式白名單接受與拒絕
- 樓層比對
- 含容差的尺寸分類
- 來源明細表去重
- dry-run 阻擋狀態訊息

COM 測試要用複本活頁簿。第一次驗證絕對不要直接對使用者原始活頁簿下手。
