# 門檻開口統計 Lessons

## L-001：門檻統計必須檢查門兩側房間

不鏽鋼門檻統計時，房間排除不是主要房間過濾。只要 `FromRoomName` 或 `ToRoomName` 任一側符合排除房間規則，該門就必須排除。這可避免「有效房間 ↔ 排除的服務空間/廁所/機房」之間的門被誤計。

## L-002：`類型備註` 是門編號分組鍵

在此工作流中，使用者將門類型參數 `類型備註` 當作門編號。除非使用者要求改用其他分組鍵，否則不要改用實體 `標註`、實體 `備註` 或 `TypeMark`。

## L-003：類型排除與房間排除分開處理

有些門即使相鄰房間通過，也應因類型/族群文字而排除。本工作流常見例子包含類型/族群文字含 `管道間` 或 `鐵捲門`。此規則應在房間兩側過濾後、分組前套用。

## L-004：規則變更會使先前總數失效

使用者新增或修改排除條件時，必須重新查詢或由本回合工具輸出重新推導。除非所有受影響項目都出現在本回合工具輸出中，否則不要用心算修正先前表格。

## L-005：窗戶功能先保留為通用模式

相同的房間/開口模式可透過 `get_room_window_counts` 用於窗戶，但不要預設窗戶具有門檻統計的業務邏輯。當使用者需要窗戶衍生數量時，再詢問實際應用規則。

## L-006：無關的門不得成為 blocker（2026-07-27）

機房門檻長度只由「碰到勾選機房」的門構成。專案裡沒有房間關聯、或缺寬度的其他門，
是與本工項無關的雜訊，不可列入 blocker 擋住更新——否則使用者永遠無法寫入。
只有「已納入但缺有效寬度」才是真實資料缺口。

配套：blocker 訊息要帶得出門的身分（ElementId ＋兩側房號房名），
只給 ElementId 使用者仍要自己回 Revit 慢慢找。

## L-007：英數關鍵字要有字詞邊界（2026-07-27）

房名正規化會把空白與 `-`、`_` 全部刪掉，`SERVER ROOM` 會變成 `serverroom`。
此時若用子字串比對 `ups`/`mdf`/`ahu`/`mau`，`GROUPS`、`MAUSOLEUM` 會被誤判成機房。
解法是另外保留一份「分隔符號換成空白」的正規化字串，英數關鍵字在這份上做字詞邊界比對，
中日文關鍵字仍在「刪除分隔符號」的字串上做子字串比對（`消防 泵房` 要能命中 `泵房`）。

## L-008：多階段模型要問門自己的階段（2026-07-27）

`get_FromRoom(phase)` / `get_ToRoom(phase)` 依階段回答不同房間。
若照文件的 `doc.Phases` 順序逐一嘗試並取第一個非 None 值，會拿到這樘門在自己階段裡
根本沒碰到的房間。正確順序是先問門的 `PHASE_CREATED`，其餘階段只作備援。

## L-009：Excel 的 Find 看不到公式算出來的文字，不可用來定位工項（2026-07-27）

**這條是實測推翻的假設，優先級最高。**

原本的程式用 `ws.Cells.Find(u'門檻', ...)` 判斷「這張工作表要不要讀」，
註解還寫著「native Excel Find on it never misses a real target sheet」。
用 `物流中心工項-0720.xls` 實測，這句話是錯的：

- 全工作簿實際有 5 個含「門檻」的儲存格，Find 只看得到 2 個。
- 漏掉的 3 個共通點是「儲存格值來自公式」——計算表 `其他長度!C19` 的內容是
  `=小計!C93`，算出來才是 `不銹鋼門檻(機房)`。
- `LookIn=xlValues` 與 `xlFormulas` 都找不到；先呼叫 `Application.Calculate()`
  或 `ws.Activate()` 也沒用。
- 但 `Range.Value2` 讀得到正確的快取結果。

而**唯一可寫入的目標 `其他長度!F19` 正是被漏掉的那一個**——
等於這顆按鈕在這份實際預算表上，原本永遠定位不到工項。

結論：定位一律用 `UsedRange.Value2`（每張表一次 COM 呼叫）再在 Python 端比對。
實測成本 2.8 秒 / 74,485 格 / 19 張表，載入時跑一次可以接受。
讀取上限被觸發且該表含工項時，要當成「無法確認唯一」列為 blocker。
不要因為「Find 比較快」再改回去。

## L-013：.xls 的函式引數上限是 30，不要用 SUM 寫門寬（2026-07-27）

實機第二次失敗停在「寫入公式」階段，一樣是無訊息的 `0x800A03EC`。
在 `物流中心工項-0720.xls` 副本上用 Excel 16.0 實測（二分搜尋）：

| 檔案格式 | `=SUM(a,b,c…)` | `=a+b+c…` 加法鏈 |
|---|---:|---:|
| .xls（BIFF8） | **最多 30 項** | 最多 180 項（約 720 字元）|
| .xlsx | 255 項 | 400+ 項 |

Excel 97-2003 格式每個函式最多 30 個引數，所以 `=SUM(w1,…,w31)` 必然失敗。
機房門通常遠超過 30 樘——**這代表用 SUM 的版本在任何真實專案的 .xls 上都不可能成功**，
只有測試用的小樣本會過。

原表 `其他長度!F19` 本來就是 45 項的加法鏈，不是 SUM——做表的人早就撞過這道牆。
所以正確寫法就是跟著表格的既有慣例走：

1. 預設輸出加法鏈 `=0.9+1.8+…`（每樘門一項，可逐筆稽核，且與原表風格一致）。
2. 超過該格式的字元預算時，退回分組式 `=120*0.9+80*1.8`（數量×單長，總數不變）。
3. 兩種形狀都必須列入 `is_safe_length_formula` 白名單，
   否則下一次執行會因為「原公式不在白名單」而拒絕覆寫自己上次寫的結果。

## L-012：在 Revit 裡不要反覆開關 Excel 實例（2026-07-27）

實機按下「更新 Excel」時出現 `COMException (0x800A03EC)`，IronPython traceback
沒有行號完全看不出位置。用「檔案沒變、也沒產生備份檔」反推，才定位到失敗發生在
`shutil.copy2` 之前——也就是 `update_workbook` 開頭那次「更新前重驗」的 Excel 開啟。

原設計一次更新要開關 Excel **四次**（載入預覽、更新前重驗、寫入、回讀驗證）。
CPython 腳本跑得過，是因為進程短命；Revit 是長生命期宿主，
前一個 `Excel.Application` 還在關閉中就 `Activator.CreateInstance` 建新實例，
就會拿到這種沒有訊息的 `0x800A03EC`。

作法：把「定位」拆成吃 `workbook` 的純函式，更新流程只開一次 Excel（讀寫模式），
在同一個 session 裡完成重新定位 → 寫入 → 重算 → 存檔 → 回讀驗證。
另外一定要加階段標記（開啟／定位／寫入／重算／存檔／回讀），
否則下次再出現無訊息的 COM 例外，又要靠副檔案痕跡反推一次。

## L-011：預算表的工項標籤常是跨表公式鏡像（2026-07-27）

同一個工項名稱在 `物流中心工項-0720.xls` 出現在三處，關係是：

```
其他長度!C19 = 小計!C93（計算表）   <- 唯一可寫入
小計!C93     = 字面字串（彙總表）
更新工項!B114 = 小計!C93（對照表）
```

真正的輸入格在計算表：`其他長度!F19`（長），同列 `E19` 是數量、
`G19 = ROUND(E19*F19,2)`、`N19` 再回流到 `小計!H93`。
所以「同一工作表上方要找得到 數量/長度 表頭配對」這條篩選是有效的——
彙總表與對照表沒有這組表頭，自然被排除。不要改成「取第一個命中的標籤」。

## L-010：寫入失敗要自動還原（2026-07-27）

備份是程式自己在幾秒前複製的，寫入或回讀驗證失敗時直接還原即可，
不要只丟一句「請由備份復原」給使用者。還原後備份檔仍保留。

## L-014：數量要引用工作簿自己的索引欄，不要寫死數字（2026-07-27）

使用者要求：F19 不要寫一串沒有出處的數字，要引用 `內牆` 分頁的開口寬度欄，
「比較有一個依據」。實測後這不只是可讀性問題，而是**結構正確性**問題：

`其他長度!F20`（一般門檻）本來就是 `=SUM(內牆!M16:M484)-F19`，
所以 `F19 + F20` 恆等於 M 欄總和。F19 少算多少，
就有多少機房開口被當成一般門檻計價。實測 F19=48.00（Revit 門寬）時，
內牆 判定的機房列合計是 75.60，等於 27.6 m 被算到 F20 去了。
只有 F19 也引用同一欄，兩列才會精確切分。

實作要點：

1. **索引分頁與寬度欄要探索，不可寫死**。判準是「房間表頭 `編號`/`空間名稱`
   ＋右側唯一的 `寬` 欄」。本案同時命中 `內牆!M`（355 列）與 `踢腳!F`（366 列），
   所以必須讓使用者選——但預設值可以從工作簿自己推：
   掃描相鄰工項列既有公式引用了哪一張，`F20` 就寫著 `內牆!M`。
2. **一個房間佔一段列**，只有第一列重複 `編號`/`空間名稱`，
   後續開口列留白，要往下沿用最後看到的房間。
3. 連續列壓成區段後，**每段各自一個 SUM 再用 `+` 串接**
   （`=SUM(內牆!M16:M20)+內牆!M30`）。本案 50 列壓成 30 段，
   如果寫成單一個 `SUM(段1,段2,…)` 就是 30 個引數，剛好卡死 .xls 上限。
4. 寫出去的引用式必須被 `is_safe_length_formula` 認得，
   否則下一次執行會拒絕覆寫自己上次的輸出。放寬的範圍要精確：
   只接受「單一分頁、單一欄」的引用鏈，
   `=SUM(內牆!M16:M484)-F19` 這種含減法或跨欄的仍要擋下。
5. 讀整張索引分頁的成本可忽略：內牆 485 列 × 28 欄實測 0.01 秒，
   而且掃描本來就會讀過每張分頁。

## L-015：連結模型的房間會撞號，「內牆」索引可能涵蓋主模型抓不到的棟別（2026-07-30）

實測 `物流中心工項-0720.xls` 時發現：`01C棟B1空間表`（鮮食中心 C棟 B1F，房號 B135–B151）
裡的機房（B139/B142/B144/B145/B147/B149）**完全不在主模型裡**，只存在於已載入的連結模型
`U-PARK-AR-鮮食中心.rvt`（LinkInstanceId 11128732，191 間房）。

但 Excel 的 `內牆` 開口寬度索引是全案共用、不分棟別的，這 6 間機房的開口列本來就在
`內牆` 裡（r74/80/82/83/87/89，合計 5.4 m）。所以：

- **F19 若只重建 `內牆` 分頁本身的房名分類**（不依賴 Revit 回讀），會自動涵蓋到 C棟，
  因為索引本來就沒有分棟。2026-07-30 用這個方法修復出 47 列、73.80 m，是完整值。
- **按鈕目前的流程**（`collect_rooms` 只收主模型 → 使用者勾選 → 對 `內牆` 選列）
  只會拿到主模型的 285 間房，勾選畫面上根本不會出現 B139 等 C棟房間，
  於是只算出 37 樘 / 48.0 m——**少了 C棟整批機房，且使用者在 UI 上看不出少了什麼**，
  因為那些房間從未被列出過，不是「有列出但沒勾選」。

**危險的連帶問題**：房號會跨模型撞號，且指的是完全不同房間。
同一個房號在兩份文件裡：

| 房號 | 主模型 | 鮮食中心連結模型 |
|---|---|---|
| F125 | 電氣室（機房） | 女廁 |
| F131 | 資訊機房（機房） | 安全梯樓梯間 |
| F133 | 資訊機房（機房） | 客梯 |

現有 `room_matches`／`select_opening_rows` 用「房號＋房名」雙鍵比對，這條防線本來就在，
但**加入連結模型支援時絕不能只用房號比對**，否則會把連結的女廁誤判成主模型的電氣室。

**實作狀態（2026-07-30 已完成程式面，尚未在實模型驗證）**：

1. ✅ `collect_rooms(doc, selected_link_ids, selected_level_keys)` 收主模型＋勾選的連結模型，
   房間身分改為 `logic.room_uid(來源, ElementId)` 複合鍵，樓層為 `logic.level_key`
   （比照 `door_window_excel.py` 已驗證過的模式）。回傳 `(rooms, scopes)`，
   `scopes` 讓 UI 說得出每個模型各自抓了哪些樓層、幾間房。
2. ✅ UI 加「選擇連結模型…」「選擇樓層…」兩個多選；不勾＝全抓。
3. ✅ `collect_doors(doc, selected_rooms)` 依來源分組，各自在自己的文件內找門；
   門紀錄帶 `key`，`summarize_doors` 改用複合鍵去重（ElementId 會跨文件重號）。
4. ✅ 索引比對維持房號＋房名雙鍵，未動 `room_matches`。
5. ⏳ **尚未在實模型跑過**。下一次開 Revit 時要驗的：勾 `U-PARK-AR-鮮食中心.rvt` ＋
   只勾它的 B1F，預期在房間清單看得到 B139/B142/B144/B145/B147/B149 這 6 間機房，
   且 `內牆` 索引選列後 F19 應回到 47 列 / 73.80 m（＝主模型 37 樘的 48.0 m ＋ C棟 5.4 m
   ＋其餘依實際勾選）。在這個數字對上以前，仍**不要用按鈕整批覆寫 F19**
   （現值為 2026-07-30 的修復值 73.80 m，見 log 2026-07-30 16:12）。

**兩個實作時才浮現的設計決定**（都寫進 `domain/threshold-opening-takeoff.md`）：

- **樓層篩選是逐模型生效**，不是全域。`door_window_excel.py` 的 `source_has_selection`
  語意是「有選樓層但沒有一個屬於這個來源 → 整個來源略過」，照抄過來的話，
  使用者只勾連結的 B1F 就會讓主模型 285 間房整批消失——正好重演這條 Lesson
  要修的病（使用者在 UI 上看不出少了什麼）。所以這裡改成
  `level_filter_for_source()`：某來源沒勾任何樓層＝該來源全部樓層。
- **重新收集房間時要保留使用者已勾選的狀態**（依 `key` 對照），
  否則每次改連結/樓層選擇都會把手動勾選洗回規則預設值。
