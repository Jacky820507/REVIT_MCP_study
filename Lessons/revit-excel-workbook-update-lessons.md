# Revit 既有 Excel 活頁簿更新 Lessons

## L-001: 既有活頁簿是合約，不是空白輸出

更新估價活頁簿時，畫面上看到的總數只是最後一步。真正的合約包括列標籤、公式、倍數欄、跨分頁參照與人工維護儲存格。動手寫程式前一定要先讀活頁簿，除非使用者明確要求，不然每一條公式都要保住。

## L-002: 列號是證據，不是身分

在觀察到的停車位活頁簿中，數量落在 `其他數量` 第 8 到 14 列，但未來活頁簿可能插列或移位。應以正規化項目文字加尺寸比對，再驗證唯一性。列號只能作為預覽中最後解析出的目標結果。

## L-003: 明細表比類別更能定義範圍

原始 Revit 停車類別元素可能混入非車位圖形或輔助符號。若使用者指定 `汽車停車數量`、`大客車停車數量`、`機車停車數量` 這類明細表，就應把這些精確明細表視為來源邊界，並在計數前先對元素 id 去重。

## L-004: 使用者倍數應該放在 UI

塑膠車輪檔可能是每格 1 個，也可能是 2 個。這不是模型事實，而是專案或採購慣例。應把它做成 UI 選項，在預覽中顯示乘算結果，並寫入倍數儲存格，而不是硬編規則。

## L-005: 公式儲存格需要白名單

光檢查「有公式」還不夠。在寫入數量或倍數儲存格前，要先把公式正規化，再和預期合約比對，例如 `Frow*Grow` 或 `PRODUCT(Frow,Grow)`。若公式含有非預期參照或商業邏輯，就要拒絕該列。

## L-006: COM 驗證可能比邏輯測試慢很多

舊版 `.xls` 活頁簿可能必須依賴 Excel COM 才能可靠重算公式，但完整重開驗證在大型檔案上可能很慢，甚至逾時。要把單元測試留在純邏輯層，COM 測試則對複本活頁簿執行。若 live COM 驗證做不完，就要明確回報這個限制。

## L-007: 跨分頁索引驗證是必做項

如果 `小計` 已經沒有正確索引到預期列或工作表，那麼只更新 `其他數量` 仍然算半套。回報成功前，必須一起驗證來源列、公式與小計或索引分頁。

## L-008: Revit 單位一定要寫清楚

停車位列標籤使用公分，而 Revit 尺寸常是毫米或 internal feet。應在分類邊界只做一次轉換，並保留書面容差。不要把顯示字串直接當成模型尺寸來比較。

## L-009: Markdown 知識文件不要為了 Windows 工具改成 cp950

知識型 `.md` 文件和 legacy Excel 活頁簿是兩種完全不同的東西。前者應維持 UTF-8，後者才可能需要和 Excel COM 或舊式編碼相容。不要因為某個 Windows 驗證腳本預設用系統編碼，就把整份知識文件強制轉成 cp950；這樣很容易把繁體中文直接寫壞成問號。

## L-010: 先修讀取端，再考慮資料端

當文件顯示亂碼時，要先確認是讀取方式錯誤，還是檔案內容已被實際污染。像 `Get-Content -Encoding Default`、Python `open()` 預設編碼、或舊腳本未指定 UTF-8，都可能只是「讀錯」。只有在 hex 或多種編碼讀法都確認內容被替換成 `?` 時，才應重建檔案內容。

## L-011: Revit 群組會放大逐元素掃描成本

停車位放在 Revit 群組內時，元素數量與參數讀取成本會一起放大。Excel 更新按鈕不應對每個元素掃描 `Parameters` 全集合，也不應展開群組再重算。先用明細表邊界、樓層、尺寸與 `ElementId` 去重完成快速分類；只有分類失敗的元素才讀取額外文字參數。若偵測到群組內元素，預覽要明確回報群組數量，讓使用者知道慢速來源但仍可放心數量邊界。

## L-012: WPF 清單不要直接顯示 IronPython 物件

pyRevit 的 WPF ComboBox/ListBox 若直接綁 IronPython 自訂物件，畫面可能顯示 `IronPython.NewTypes.System.Object...` 這類型別字串，而不是使用者能理解的名稱。UI 清單應優先綁純文字 label，內部用 `SelectedIndex` 或 label map 找回原始物件。

## L-013: 停車 Excel 來源不能寫死三張明細表

`汽車停車數量`、`大客車停車數量`、`機車停車數量` 只是曾觀察到的專案慣例，不是永久合約。UI 應提供自動偵測指定樓層所有 Parking 元素的模式，並提供明細表複選模式給專案特殊分類使用。複選多張表時必須用 `ElementId` 去重，且預覽要列出每個來源實際納入數量。

## L-014: 公式驗證失敗也要讓預覽出來

Revit 數量與 Excel 活頁簿檢查是兩個不同層次。若目標列 H/I/J 公式鏈不符合白名單，預覽不應直接跳錯結束；應在預覽框列出實際公式與阻擋原因，並保持更新按鈕停用。這樣使用者能先確認 Revit 數量是否合理，再決定要修公式或擴充白名單。

## L-015: 明細表清單不要過度關鍵字過濾

如果 UI 提供「選取明細表」模式，就不應只列出名稱含 `停車`、`車位` 的明細表；專案命名常有縮寫、英文、代碼或分包前綴。較好的做法是列出所有非樣板 ViewSchedule，把停車候選排前面並預選，但仍讓使用者能選到任何實際存在的明細表。

## L-016: 共用地下室常需要讀 Revit 連結模型

物流、廠房或多棟建築專案的地下室可能是共通模型，車位不一定存在於 host document。停車 Excel 或類似數量按鈕應提供「包含 Revit 連結中的元素」選項。讀取連結元素時，`ElementId` 去重要帶上 link instance id，樓層比對也不能只用 host LevelId，需使用樓層名稱或高程輔助。

## L-017: Parking 類別可能混入箭頭與標誌

自動偵測 `OST_Parking` 時，可能會抓到 `AE-行車方向標誌`、箭頭或標誌族群。這些不是停車位，不應列為未分類阻擋更新。若元素沒有停車位尺寸，且名稱明確是方向標誌或箭頭，應歸入「已忽略非車位 Parking 元件」，並在預覽中回報數量。

## L-018: 指定連結與明細表篩選是兩層不同的邊界

共用地下室可能同時載入多個具有 B1F 的 Revit 連結，因此「包含所有連結」會把不相關車位一起加總。正確做法是讓使用者明確複選連結實例，並把主模型明細表與指定連結視為兩種獨立來源：主模型使用明細表邊界；指定連結則只在已選連結內依樓層、Parking 類別與尺寸分類。不要把主模型明細表的 `標註等於汽車停車` 直接套到連結，因為實案證明連結模型的同名欄位可能是 `611`、`682` 這類車位編號，結果會把全部連結車位錯誤排除。明細表與連結清單較長時，應由主 UI 的按鈕開啟獨立多選視窗。

## L-019: 目標數量欄本身也可能是應保留的公式

既有活頁簿的 F 欄不一定全部是人工輸入；例如塑膠車輪檔基數或無障礙車位可能由其他列、其他分頁公式帶入。遇到公式時不能直接覆寫，也不能只因本次重算結果剛好等於 Revit 數量就放行。預覽必須顯示完整公式；只有公式來源與形狀經審查並加入白名單後，才可保留公式、只寫其他輸入格，並在存檔前後同時驗證公式文字沒有改變且結果符合預期。

## L-020: 輪檔列 F 欄若已內含倍率，G 欄不能再寫相同倍率

停車位 Excel 可能把塑膠車輪檔的 F 欄做成 `=SUM(F9:F12)*2` 這種「汽車位合計 × 輪檔倍率」公式。這時 F 欄已經是輪檔總數，若工具又把 G 欄寫成 2，H 欄 `F*G` 會再次相乘造成數量翻倍。遇到這種白名單公式時，應保留 F 欄公式、驗證內含倍率等於 UI 選擇，並把 G 欄寫入 1；若公式結果或倍率不符，必須在預覽階段禁止更新。

## L-021: 公式沒有錯誤值，不代表參照仍然正確

`=SUM(B2:B13)` 在資料增加到第 14 列後仍會正常算出數字，所以只掃 `#REF!` 抓不到少算。列號只能是由唯一標籤、欄名與資料 key 最後解析出的結果；總計公式要逐欄驗證範圍正好等於資料區，跨分頁總計參照要掃整本活頁簿並跟著總計標籤重定位。測試必須主動插入標題列、資料列與重排材料欄，確認公式語意不變，而不是只確認 Excel 能開啟。
